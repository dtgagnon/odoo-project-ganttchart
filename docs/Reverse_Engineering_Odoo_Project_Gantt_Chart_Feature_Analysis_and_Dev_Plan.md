# Reverse Engineering Odoo’s Project Gantt Chart Feature

*Figure: Odoo’s Project app Gantt chart view (grouped by assignee) with tasks scheduled on a timeline and a dependency arrow linking two tasks.*

## Stakeholder Needs and User Requirements

In Odoo Enterprise, the Project module’s Gantt chart is a powerful project planning tool designed to meet the needs of project managers and teams. Based on our analysis of Odoo’s official documentation and demos, we can identify several key user requirements and use cases driving this feature:

- **Visual Timeline Planning:** Users (typically project managers) need to see tasks laid out on a timeline (calendar) to understand project schedules and overlaps. The Gantt chart provides a clear visual representation of tasks with their start and end dates as horizontal bars. This helps in **spotting overlaps, gaps, and the overall timeline** of the project.

- **Drag-and-Drop Scheduling:** A core requirement is the ability to easily adjust schedules. Users can **drag and drop task bars** to new dates or extend/shrink their duration directly on the timeline. This interactive adjustment instantly updates the task’s planned dates, making it easy to reschedule tasks or change deadlines. During drag operations, Odoo even shows tooltips with the new start/end dates for precision and displays the dates on the bar for clarity.

- **Task Dependencies (Predecessors/Successors):** Project managers often need to enforce logical order between tasks. The Gantt feature allows linking tasks with **dependencies** so that certain tasks can only start after others finish. Users can create dependencies by clicking and dragging from one task to another (small connector “dots” appear on hover) to draw an arrow linking a predecessor to a successor. This visual link (arrow) indicates the dependency relationship on the chart. The system then enforces these dependencies: any task that has unfinished predecessors is automatically marked as “waiting” and cannot be moved to an In Progress/Started state until the blockers are completed or cleared. This **blocked/waiting status** ensures team members don’t start tasks out of order, addressing a key stakeholder need for **workflow enforcement and proper sequencing**.

- **Automatic Scheduling Adjustments:** With dependencies in place, users expect the schedule to behave intelligently. Odoo’s Gantt meets this need by **preserving dependencies when tasks are rescheduled** – e.g. if you move a predecessor task later, the system can automatically shift the successor task accordingly to maintain the dependency gap. In Odoo 19, the Gantt view introduced the concept of **“buffer time”** between dependent tasks: when you reschedule linked tasks, you can choose whether to keep or adjust any buffer (lag) between them. This allows realistic scheduling, accounting for mandated gaps or lead times. It reflects stakeholder needs for **flexible yet controlled scheduling** – project managers can build in buffer days between tasks and maintain them even as schedules change.

- **Resource Assignment & Workload View:** The Gantt chart addresses the needs of resource managers by enabling grouping of tasks by resource/assignee. In practice, users can group the Gantt view by **assignee (responsible user)**, by project, or other criteria. When grouped by assignee, each row represents a team member, and their tasks appear along that row’s timeline. This helps visualize each person’s workload and identify overbooking or idle gaps. The interface allows scheduling tasks directly for a specific user: if you click on a timeline slot under a particular assignee’s row, the system opens a scheduling dialog filtered to that user’s tasks. This feature ensures that when a manager is assigning unscheduled tasks to a user via the Gantt, they only see relevant tasks for that user, streamlining the workflow. Stakeholders (resource managers, team leads) need this to **efficiently allocate tasks** and ensure no one is overloaded.

- **Hierarchical Task Organization (WBS):** Projects often have sub-tasks or phases. The Gantt module supports a hierarchy of tasks (work breakdown structure). Users can create **sub-tasks** or group tasks into phases, and the Gantt view can display these in a nested manner (indenting sub-tasks under parent tasks). This “N-level” support allows project managers to collapse or expand task groups, focusing on high-level timelines or drilling down into details as needed. It addresses the need to organize complex projects into manageable pieces while still seeing the big picture timeline.

- **Milestones and Deadlines:** Project stakeholders need to track key dates. Odoo’s Project app supports defining **milestones** (major checkpoints/deliverables) and task deadlines. In the Gantt chart, milestones could be represented with a special icon or marker on the timeline (for example, a diamond shape) and deadlines might be indicated with an arrow or line on the chart. If a task’s deadline is exceeded, some Gantt implementations highlight it (e.g. colored indicators or an overdue label). These features ensure managers don’t miss critical dates and can visually see how tasks align with milestone targets.

- **Time Scaling and Zoom:** Different stakeholders require different timeline scopes – some want a high-level plan (months or quarters), others need day-to-day scheduling. The Gantt view provides **zoom levels** (e.g. switch between viewing by month, week, day, or even hours). Odoo 19 adds an *intelligent zoom* that automatically adjusts the timeline scale to fit the context or screen, making it easy to navigate large timelines. Users can zoom in for detail or zoom out for an overview, which is crucial for both short-term planners and strategic planners.

- **Non-Working Time & Availability:** A realistic scheduling tool must account for non-working periods (weekends, holidays, off-hours) and user time off. Stakeholders want the chart to reflect when work *cannot* happen. Odoo’s Gantt addresses this by visually distinguishing non-working times – for example, shading weekends or letting users *fold “off-hours” out of view*. In Odoo 19, there is an option to **collapse off-hours** in the timeline to maximize visible working time. Similarly, an assignee’s approved leaves or company holidays could be shown as blocked periods (or highlighted segments) on that person’s row (the OBS blog described this as making “absences collapsible” for realism in planning). This ensures that when scheduling, managers don’t inadvertently plan work when resources are unavailable.

- **Task Progress and Status Management:** Project stakeholders often want to track progress % and status directly on the timeline. While Odoo primarily uses stages (“To Do”, “In Progress”, “Done”), the Gantt view can reflect status via color codes or icons on the task bars. For example, tasks marked done might appear in a different color or with a checkmark. If using progress percentages, a task bar might show a filled portion indicating how much is completed. The **tooltip** on each task bar in Odoo’s Gantt can display details like the task’s stage, progress, and constraints. This helps stakeholders see not just timing but also how far along each task is and if it’s blocked or at risk. Additionally, because Odoo’s dependency feature puts tasks in a **“Waiting” state when blocked**, project managers are immediately aware of which tasks are waiting on others (often indicated by a special status or an icon on the Gantt bar).

- **Real-time Collaboration and Permissions:** Multiple roles interact with projects, so the system must handle permissions. Typically, **project managers** can edit the schedule (move tasks, set dependencies), whereas regular project users or external collaborators might only view the Gantt or make limited changes. Odoo’s security model likely enforces this: only users with sufficient access rights (e.g. Project Managers group) can modify task fields like planned dates or dependencies. From a requirements standpoint, the Gantt feature needs to respect these permission rules – e.g. the drag-and-drop and linking should be disabled or read-only for users who aren’t allowed to schedule tasks. Stakeholders like PMOs also need the ability to **export or print** the Gantt chart for reporting. Indeed, Odoo allows printing the Gantt via the standard print menu (generating a PDF of the timeline), since sharing the plan with stakeholders outside the system is often required.

- **Ease of Use & Error Correction:** Since interactive scheduling can be complex, the users need safety nets. Odoo’s Gantt view provides an **Undo/Redo** capability for scheduling changes. For example, if a manager accidentally moves a task to the wrong date or links the wrong tasks, they can quickly undo that change (reverting the timeline to its prior state). This feature is critical for user confidence, letting them experiment with scheduling “what-if” scenarios without fear of messing up data. The interface also likely includes quick actions like **add/delete task** from the chart and editing of task details via a popup or form (e.g. double-clicking a task bar opens the task form or a quick editor). All these usability features ensure the tool is **efficient and user-friendly**, matching stakeholders’ expectations for a modern project management tool.

In summary, the Gantt chart feature in Odoo Project is driven by the need for a **visual, interactive, and intelligent scheduling tool**. It must support drag-and-drop planning, enforce task dependencies and order, allow resource-centric views, handle hierarchical projects, and adapt to real-world scheduling constraints (working hours, absences), all while being easy to use and aligned with user permissions. These requirements set the stage for the system’s architecture and design, which we reverse-engineer next.

## System Architecture and Technical Design

Recreating Odoo’s Gantt chart functionality requires understanding how the feature is structured in the Odoo ecosystem. Odoo follows a Model-View-Controller (MVC) architecture within its framework, and the Gantt chart is implemented as a specialized view type on top of the project management data models. Based on documentation and known Odoo design patterns, we can infer the following about the architecture and components:

- **Data Model (Models layer):** The primary model involved is `project.task` (the Task model) enhanced with scheduling fields and relationships for dependencies. In Odoo Enterprise, two datetime fields exist on tasks to define the schedule: typically named **Planned Start** and **Planned End** (often `planned_date_begin` and `planned_date_end`). These fields store the position of the task bar on the Gantt timeline. They likely are set to date or datetime type (depending on whether hour-level scheduling is supported; given off-hours and potentially hour-level zoom, datetimes are probable). If both fields are empty, the task is considered unscheduled (and might not appear on the chart until scheduled). The **duration** of a task can be derived from these fields.

  For task dependencies, Odoo uses a **many-to-many self-relation** on tasks. Each task can have multiple “Blocked By” tasks (predecessors) and consequently multiple “Blocking” tasks (successors). In the UI this is shown as a *Blocked by* tab and a smart button for *Blocked Tasks*. Under the hood, this could be a field like `blocked_by_ids = fields.Many2many('project.task', 'task_dependency_rel', 'task_id', 'depends_on_id', string="Blocked by")`, which creates a relationship between tasks. Odoo likely manages the inverse (tasks that are blocking others) via this relation (perhaps using the many2many’s reverse logic or an auxiliary computed field for “Blocked Tasks”).

  Additionally, the **task state/stage** logic is extended to account for dependencies. Odoo’s Project module typically uses a stage field (kanban stages), but they introduced a notion of **“Waiting” state** when a task has unfinished dependencies. This could be implemented either as a special stage (e.g., a stage named “Waiting” that the task auto-moves into), or more likely as a separate boolean or status field. Since Odoo’s documentation explicitly says “Successor tasks are assigned the *Waiting* status and cannot be moved to In Progress until predecessors are done”, it suggests there is logic to dynamically prevent changing stage if blocked. The implementation could be:
    - A compute on a field `is_blocked` or an automated action that flags the task as waiting if `blocked_by_ids` contains any tasks not in done/cancelled.
    - UI logic (on Kanban or form view) that disables the “start” action for waiting tasks, perhaps with a tooltip “This task is waiting for another task to be completed.”
    - Possibly integration with stage changes: if a user tries to move a blocked task into a stage marked as “In Progress” (or any stage that is a started stage), the system could raise a warning or automatically revert it. (The Odoo forum discussions indicate that marking a blocked task as done might have some warnings if done out of order).

  The data model also needs to integrate with other modules for a realistic schedule:
    - **Resource/Assignee**: The `user_id` (assignee) field on tasks is used for grouping and possibly for checking resource availability. No changes needed here except to utilize it in views.
    - **Calendars/Working Time**: Odoo has a concept of work calendars (resource calendar for business hours) and the Time Off module for leaves. While not explicitly stated in docs, the Gantt likely takes into account the company or project calendar for off-hours. The “fold off-hours” feature suggests that the system knows which hours are non-work (possibly defined by a calendar). It might simply hide evening/night hours on a day-view timeline, or skip weekends entirely when zoomed to weeks. This implies the Gantt view has access to a calendar of working hours (possibly the one set on the project or globally) to decide what to fold. Similarly, integration with the *Time Off* (leaves) could mark certain days for a user as unavailable. This might not require new fields on task, but the Gantt view component could query the Time Off model for absences of each user and overlay that on the chart (for example, shading the period or showing a label “On Leave”). The OBS mention of “absences are collapsible” aligns with this integration.
    - **Milestones**: Odoo has a `project.milestone` model in newer versions (used to track key dates in a project). If so, the Gantt view might fetch milestones and display them. Alternatively, milestones could be represented as tasks of a special type (flagged as milestone) and thus appear as zero-duration bars or special icons. Either way, the Gantt data model likely includes fetching these items along with tasks to display on the timeline.

- **View and Controller Layer:** Odoo’s web client defines a **Gantt view** type (only available in Enterprise). Under the hood, there is JavaScript code (likely an OWL or legacy JS widget) that renders the Gantt chart canvas. This component would be part of the `web_gantt` module (or similar) in Odoo Enterprise. Key responsibilities of this component:
    - **Data Loading:** It queries tasks (and possibly related data like milestones or absences) via Odoo’s web framework (probably using an RPC call to read `project.task` records with their planned dates, names, progress, etc., filtered by the current project or domain the user sets). If grouping is applied, the data might be grouped by that field server-side or organized client-side.
    - **Rendering:** The view renders a timeline grid. Typically, a Gantt chart uses an HTML `<canvas>` or SVG for the chart portion and regular HTML for the left-side list. Odoo likely uses an HTML/SVG approach for easier DOM updates (some third-party Odoo Gantt modules use libraries like DHTMLX or Bryntum which generate the chart).
      - The **left panel** lists tasks or group headings (like assignees or project names) in a tree structure. This panel likely shows task names (and possibly icons for sub-tasks, or expansion toggles if hierarchical). It may also show additional info like duration or progress percentage.
      - The **right panel** is the time grid. It has a time scale header (days, weeks, etc.). Each task is drawn as a bar whose position and length correspond to its start and end date. Task bars might be color-coded or carry icons (e.g., a small icon if the task is in a certain stage or if it’s waiting on something).
      - If tasks have subtasks, parent tasks could be rendered as summary bars spanning the min to max dates of their children (some Gantt charts do this). It’s unclear if Odoo does that natively, but “supports N-levels” suggests at least the structure is shown.
      - **Dependency lines** (arrows) are drawn connecting task bars. Likely implemented as SVG path lines or a canvas drawing that connects the end of one bar to the start of another. These lines have interactive elements: as per docs, hovering a dependency arrow shows a little “x” button in the middle that allows deletion of that dependency link easily.
    - **Interactivity:** The Gantt view JS handles user interactions:
      - **Dragging a task bar:** On drag end, it calculates the new start/end dates and sends an update to the server (write to `planned_date_begin`/`end`). The update might happen immediately (each drop triggers an RPC call to save changes). Odoo 19’s addition of *Undo* suggests the client might also maintain a history of moves. Possibly, the change is applied on the client and the old value stored, and an “undo” button triggers another write to revert to old dates. This could be done via the browser’s memory without a full undo log on the server.
      - **Resizing a task bar:** If supported (dragging the edge of a bar to extend or shorten duration), similar logic applies – update end date (or start date if left edge moved) and save, with possible undo.
      - **Creating a dependency:** When the user drags from the dot of one task to another task, the client sends a command to create a link. This likely calls a server method to add the target task into the source task’s `blocked_by_ids` (or vice versa). Immediately, the UI draws the arrow. The server might in response also update the successor task’s status to waiting if the predecessor isn’t done. (In Odoo, this could trigger an update of a state field or a stage change as discussed.)
      - **Unscheduling or removing scheduling:** If a user wants to remove a task from the timeline (unschedule it), perhaps dragging it off or clearing dates via an edit form is needed. Odoo might not allow empty planned dates from the Gantt UI directly, but an edit form could clear them.
      - **Adding/scheduling a task from Gantt:** If a task has no dates (newly created in backlog), Odoo provides a way in the Gantt to place it. The Cybrosys tutorial shows that clicking an empty cell in the chart opens a wizard to choose an unscheduled task to place. The system pre-filters tasks in that dialog by context (e.g., if you clicked under *Marc Demo* on Feb 10, it will show tasks assigned to Marc Demo that are not yet planned). Upon selection, it sets that task’s start date to the clicked date and possibly a default duration (maybe 1 day or as per task’s planned hours). This scheduling wizard is part of the controller logic bridging user input to model update.
      - **Editing task details:** There may be a quick popup on clicking a task bar (as Ksolves module highlights, likely Odoo also has something similar). For full detail, users can probably double-click a bar to open the standard task form view in a dialog, where they can edit fields (including assignee, duration, etc.). This is standard Odoo behavior for most views (double-click to edit record).
      - **Grouping and Filtering:** The Gantt view responds to Odoo’s regular search panel. Users can filter tasks (e.g., by project, by status, by assignee) and the chart will update to show only those tasks. They can group by fields (using Odoo’s group by feature), and the view will render group headers accordingly. The release notes specifically mention improved grouping: when grouped and adding a task, the group context is respected. Technically, grouping might be handled by the server (grouped read) and the client then draws each group as a collapsible section with its tasks. The user can likely expand/collapse groups in the left panel (e.g., collapse all tasks under a project or a user).
      - **Timeline scaling controls:** The UI includes buttons to change the scale (common icons might be “Day/Week/Month” toggle or a zoom slider). Odoo 19’s *smart zoom* might automatically change scale when you scroll or when the project span changes, but usually, there are explicit controls too. The *“Zoom to Fit”* function mentioned in third-party apps could be present or planned – fitting all tasks in view.
      - **Today Marker and Navigation:** Likely a vertical line highlights the current date (“Today”) on the chart for orientation. Navigation arrows or a date range selector allow moving the timeline window (e.g., go to next month or scroll horizontally). The screenshot and Odoo UI typically show navigation buttons (e.g., back/forward, “today” focus, and a date range display). These help users quickly jump in the timeline.

- **Business Logic and Automation:** On the server side, aside from simple field storage, there is logic to enforce rules:
    - A constraint or automation for **task dependency status**: For instance, whenever a task’s dependencies or the status of a predecessor changes, the system should update the dependent task. Odoo might use Python constraints or on-change methods. For example:
        - If a predecessor task is set to Done/Cancelled, check if all of a task’s blockers are done; if yes, automatically mark the task as no longer waiting (maybe by moving it to the next stage or enabling the user to start it).
        - If a task is marked as “In Progress” but it has blockers not done, the system could prevent that action or revert it. (This might be done via a Python `write` override on the stage field or a server action triggered by stage changes).
      This logic ensures data integrity – you can’t inadvertently break the dependency rules. The documentation confirms automatic management: “cannot be moved to In Progress until predecessor tasks are done”.
    - **Buffer time handling:** With Odoo 19’s introduction of buffer time management, there is likely some logic when moving tasks that are linked. If task B is dependent on A with, say, a 2-day buffer (meaning B is scheduled 2 days after A ends), the system might store that offset somewhere. Possibly the dependency relationship could carry a field like `delay` (number of days of gap). If so, when A is moved, the system can propose moving B to maintain the 2-day gap. The release notes say the user can choose to keep or ignore the buffer, implying a prompt or setting. Implementation-wise, when you drag A, the client or server could calculate new B date = new A end + buffer, and either auto-move B or ask the user (perhaps via a popup “Apply the same 2-day buffer for successor tasks?” with Yes/No). If user chooses to keep buffer, then update B’s dates too in one operation. This is somewhat advanced logic – likely done client-side for immediacy, with subsequent server writes to all affected tasks in one go.
    - **Non-working time skip:** If a task is dragged or extended into a weekend/off-hours and the user (or system policy) doesn’t want that, the system might automatically adjust to the next working time. It’s plausible that the system references the company’s working calendar to snap task dates to working days. If implementing, one would include logic like: on dropping a task, if its new start is on a Saturday, shift to Monday, etc. Odoo’s Planning module uses resource calendars for shifts, so similar logic could be borrowed.
    - **Integration with Calendar/Meetings:** There might be an integration where tasks with planned dates can be seen on the Odoo Calendar app or generate calendar events (some forum references suggest attempts to link tasks to calendar events). While not core to Gantt, it’s a relevant design consideration if aiming for feature parity: each task schedule could optionally create a calendar entry or at least be exportable to iCal for personal calendars. (This might not be in standard Odoo, but worth noting for completeness).

- **Security and Access:** The system architecture must respect Odoo’s security model. The Project module defines roles like *Project User* and *Project Manager*. Typically, Project Managers can edit all tasks in their projects, whereas Project Users can only edit tasks they’re assigned or cannot change certain fields. In the Gantt view, the controller likely checks permissions on each RPC:
    - When fetching tasks, it only returns those the user has read access to.
    - When writing changes (dates or dependencies), the user must have write access on that task (and possibly on the linked task for creating a dependency).
    - If a user lacks rights, the UI should either not allow the drag/link interaction or will throw an access error which should be caught and shown as a message. For example, if an external user tries to move a task, they might get a polite warning “You cannot modify this task.” This design ensures that the interactive UI doesn’t bypass back-end rules.

- **Performance considerations:** Gantt charts can become heavy with large projects (hundreds of tasks). The architecture likely addresses this by:
    - **On-demand loading:** Possibly only tasks in the currently viewed time range are loaded, and as you scroll, more tasks load (though Odoo’s default might just load all and let the browser handle it). For an initial exact re-creation, one might keep it simple (load all filtered tasks).
    - **Caching:** Odoo 19 mentions caching data for faster loading – if a user revisits a Gantt view, recently fetched data could be reused. This is a general platform improvement, but it benefits heavy views like Gantt.
    - **Simplified rendering on large data:** The “sparse mode for unscheduled tasks” suggests that if there are many unscheduled tasks (tasks with no dates), the Gantt can hide them by default to avoid clutter. This keeps the chart focused and improves performance (not drawing items with no timeline representation).
    - The UI might also limit the timeline range to the min and max dates of tasks to avoid rendering an excessively long timeline with no tasks.

In summary, the architecture is a combination of an enhanced **Project Task data model** (with scheduling fields and dependency relations), plus a rich **client-side component** that handles rendering and interaction, integrated via Odoo’s standard framework (views, JS widgets, RPC). The design leverages Odoo’s existing constructs (stages for task state, resource calendars for scheduling, security model for access) to deliver a cohesive Gantt scheduling experience. Understanding this structure allows us to plan a step-by-step implementation to recreate the feature.

## Implementation Plan

Recreating the Odoo Gantt chart feature will involve work across the back-end (data and business logic) and front-end (interactive UI). Below is a detailed implementation plan, broken into sequential phases and tasks:

**1. Extend the Project Data Model for Scheduling:**

   1.1 **Add Planned Date Fields** – Introduce two new datetime fields on the task model (if not already present in our base): `planned_date_begin` and `planned_date_end` (or similarly named). These will store the scheduled start and end times of tasks. Ensure they are included in the task form/tree views for debugging, but possibly hidden by default if empty (mirroring Odoo’s behavior where planned dates are invisible until set). Also add a computed duration field (days or hours between start and end) if helpful for display.

   1.2 **Add Dependency Relation** – Add a many-to-many field `blocked_by_ids` on `project.task` to relate tasks to the ones they depend on. Also define a complementary field `blocking_ids` (successors) either through the relation or as an inverse computed field (to easily get tasks that depend on this task). This matches Odoo’s *Blocked By* / *Blocked Tasks* concept. We will also add these to the UI: a “Blocked by” tab (one2many list of dependencies) and possibly a smart-button or indicator showing the count of *blocking* tasks (successors) for quick navigation, akin to Odoo’s smart button.

   1.3 **Sub-task Hierarchy** – If not already present, enable parent-child relationships on tasks (Odoo’s project.task has an optional parent_id for subtask). We should include this to support WBS and N-level hierarchy in the Gantt. Ensure that when a task is marked as a subtask, it appears nested under its parent in tree and potentially in Gantt.

   1.4 **Milestone Representation** – Decide how to handle milestones. One approach: treat project milestones as tasks with zero duration (planned_start = planned_end). We can add a boolean `is_milestone` on task or use a separate model. For simplicity in this phase, we might skip separate milestone records and just mark certain tasks as milestones to render differently.

**2. Implement Business Logic for Dependencies and Constraints:**

   2.1 **Automatic Waiting Status** – Implement a mechanism to mark/unmark tasks as “Waiting on dependencies.” We can do this by adding a computed boolean field `is_blocked` (True if `blocked_by_ids` contains any task not done). Also, add a corresponding **domain constraint** or override on stage changes: if a user tries to move a task to a ‘started’ stage while `is_blocked` is True, raise a validation error (or automatically move it back to a waiting stage). This ensures no one can start a blocked task. In Odoo, stages can be tagged with categories (folded, etc.); we might simply identify the “In Progress” stage by sequence or some tag to check against.

   2.2 **Cascade Completes** – When a task is marked Done or Cancelled, trigger an update on tasks that depended on it. Specifically, after writing a task’s stage to Done/Cancelled, for each task in its `blocking_ids` (successors), recompute their `is_blocked`. If none of their blockers remain, perhaps automatically notify that task’s assignee or just allow it to be started now. (Full automation to auto-start it may not be desired; better to just remove the waiting restriction and maybe move it to “Ready to Start” stage if such exists).

   2.3 **Dependency Creation/Removal Hooks** – When a dependency link is created (task A added to B’s blocked_by_ids), we might set B’s `is_blocked` = True immediately (if A not done), and perhaps move B to a Waiting stage. Conversely, if a dependency is removed, re-evaluate if B still has other blockers or not, and update accordingly. These hooks maintain consistency whether dependencies are made via UI or back-end.

   2.4 **Buffer Time Handling** – Extend the dependency model to include an optional lag. We can implement this by creating an intermediary model `project.task.dependency` that links tasks and has a field `buffer_days` (and maybe a dependency type like FS, SS for future expansion). However, to keep it simple and closer to Odoo’s likely implementation: when moving tasks in the Gantt, handle buffer in the front-end logic (see step 4.3). If we want persistence, we could store a dictionary on the task like `dependency_buffer = {predecessor_id: days}` but that complicates things. Given Odoo 19’s feature, we can assume buffer is mostly handled at scheduling time rather than stored, but we’ll design with possible extension to store if needed.

**3. Develop the Gantt Chart Front-End Component:**

   3.1 **Choose Rendering Approach** – We can either integrate an existing JS Gantt library or build from scratch. To replicate Odoo exactly, a custom implementation might be needed (since Odoo’s code is proprietary). However, using a well-supported library (like **Bryntum Gantt or DHTMLX Gantt**) could speed up development – these libraries support drag-drop, dependencies, zooming, etc. For this plan, we’ll outline a custom approach to demonstrate understanding:
      - Use an SVG element for the timeline. Each task bar is a `<rect>`, and dependency lines are `<path>` connectors.
      - The left panel (task list) can be an HTML `<div>` with nested lists or a tree to reflect hierarchy and grouping.

   3.2 **Basic Layout and Drawing** – Create the Gantt view module (e.g., as an Odoo web client widget if within Odoo, or a standalone web page if external). It should:
      - Render a header with time scale. Compute the range of dates to display (by default, perhaps project start to end or a fixed window like today’s month). Draw columns for each day/week as needed. Mark weekends/off-hours distinctly (e.g., a different background color for weekends).
      - Render each task from the dataset as a bar positioned from its start to end date. This involves converting dates to x-coordinates (needs a pixels-per-day scale). If grouped by something, group tasks together under group rows.
      - Show task names either on the bars or in the left list. Possibly truncate or abbreviate if bars are small.
      - Draw dependency arrows: for each dependency (predecessor->successor), draw a curved line from the end of predecessor’s bar to the start of successor’s bar. Add a small clickable element (like a red “x”) mid-curve for deletion action.

   3.3 **Controls and Toolbar** – Provide UI controls similar to Odoo’s: buttons for zoom levels (Day/Week/Month), a Today focus button, navigation (previous/next period), and possibly a “Fit All” zoom. Also include a button or toggle to fold/unfold non-working hours. For folding off-hours, the implementation might recalculate the timeline scale to skip evenings/weekends: e.g., compress the timeline so that Friday directly connects to Monday with no gap for the weekend (this is a bit complex but can be done by adjusting the coordinate mapping function based on a work calendar).
      - If using a library, many of these features come built-in (for instance, DHTMLX Gantt supports work-time skipping, zoom, etc., configurable).
      - Add an **Undo** and **Redo** button to the toolbar. These will call functions to revert the last change or reapply it (we maintain a stack of actions, see step 4.5).

   3.4 **Grouping and Hierarchy** – Implement the ability to group by fields. In an Odoo context, grouping can be done via backend if the user selects a grouping. For custom implementation, we might allow grouping by Assignee or Project via a dropdown. When grouping by assignee, for example, collate tasks by `user_id`. Render a row for each user with their name on the left and all their tasks on that row timeline. This means adjusting vertical positioning of bars.
      - Hierarchy (subtasks): If tasks have parent-child, we can indent child tasks under their parent in the left list. On the timeline, typically subtask bars appear as separate lines (not necessarily indented on timeline, but the left side shows structure). We can give parent tasks a summary bar (spanning all children) in a different style if desired (perhaps a thinner bar or a bracket).
      - Make group rows collapsible: e.g., allow clicking a triangle to hide tasks under a group. Collapsing would hide those bars from the timeline as well (could improve readability if many tasks).

**4. Enable User Interactions on the Gantt Chart:**

   4.1 **Drag & Drop Move** – Implement drag for task bars:
      - Capture mousedown on a task bar; on mousemove, update its position (perhaps a semi-transparent dragging clone). Provide visual feedback such as the **start and end dates in a tooltip** as you drag.
      - On mouseup (drop), compute the new start/end datetimes based on the drop location. Then update the task model: this could be done by sending an AJAX/ RPC request to update the task’s `planned_date_begin` and `planned_date_end`. For now, assume success and redraw the chart with the bar at its new position.
      - Check for dependency impacts: If this task has successors and we moved it, offer the buffer choice. For example, if Task A’s end moved from Jan 10 to Jan 15 and Task B was start Jan 11 (with effectively a 1-day gap which is now a -4 day gap), we detect that B starts before A finishes. The system can either automatically shift B to Jan 16 to preserve the sequence (and buffer if any), or at least flag it. Implementation: either automatically move dependent tasks (and mark such moves in the undo stack as well), or pop up a small notification: “Adjust dependent task start dates to maintain sequence?” with an option to apply. Given complexity, for first iteration we might auto-shift direct successors to start right after the moved task ends (preserving zero or the existing gap).
      - After dropping, record an “action” in the undo stack (store task id and old start/end so we can revert if needed).

   4.2 **Drag to Resize** – Allow adjusting duration by dragging the left or right edge of a task bar (if the user hovers near an edge, change cursor and allow horizontal resize).
      - On resize end, update the `planned_date_begin` or `planned_date_end` accordingly. (This will change duration; possibly we also update an Odoo field for planned hours if we want to tie duration to effort, but Odoo by default doesn’t auto-calc hours from Gantt).
      - Provide a tooltip of the new dates or duration while resizing (the “drag-to-resize tooltips” mentioned).
      - Add this action to undo stack as well.

   4.3 **Create/Delete Dependencies** – Implement the linking interaction:
      - When the user clicks on a task bar, show small “handle” dots (perhaps on the right edge for a predecessor link, and on the left edge for a successor link – this is how Odoo’s UI likely shows them). The user begins a link by dragging from a dot.
      - As they drag a connection line, highlight valid drop targets (tasks that would become successors). Likely restrict to not allow a task to depend on itself or create cycles (we can enforce no cycles by checking existing links).
      - On drop, if a valid target task is chosen, remove the tentative line and draw a permanent arrow connecting the two tasks. Then send a request to server to add the dependency (add predecessor to successor’s blocked_by_ids). Immediately update the successor task’s `is_blocked` status (if predecessor not done, mark successor waiting).
      - For deleting a dependency: when hovering over an existing arrow, show the small X button. If clicked, remove the arrow and send request to remove that link (update `blocked_by_ids`). Also recalc the now free task’s blocked status.
      - These changes should also be undoable: e.g., “link created” and “link deleted” can be actions to undo (which would remove or restore the link respectively). However, dependencies might be trickier to undo purely client-side because the server might enforce rules or trigger other changes. We may keep it simple: undo for dependency creation just deletes it (server call), and vice versa.

   4.4 **Add/Schedule Task from Chart** – Implement the click-to-schedule:
      - If user double-clicks or uses a dedicated “Add Task” button on the Gantt view, open a dialog. The dialog can show a list of unscheduled tasks (those with no planned dates) for the current project or domain. If the view is grouped (say by user or project) and the user invoked “add” in a specific group row or cell, pre-filter the list to that context (e.g., show only tasks of that project, or assigned to that user, as Odoo does).
      - The user selects an existing task or chooses to create a new one via this dialog. If new, gather minimal info (name, maybe assignee, etc.).
      - Upon selection, immediately set its `planned_date_begin` to the date corresponding to where the user clicked (if they clicked a specific cell on timeline, we have that date; otherwise, default to today or project start). Set a default duration (maybe one day or as per some project planning default).
      - Save and refresh the chart to display the newly scheduled task bar. The dependency arrows will also render if this new task had any or if others depend on it.

   4.5 **Undo/Redo Implementation** – Maintain an in-memory stack of recent actions (probably limit to a reasonable number of steps like 5 or 10). Each action record could be a dict like `{type: 'move', task_id: X, old_start: ..., old_end: ..., new_start: ..., new_end: ...}` or `{type: 'link', task_id: A, linked_task_id: B, created: True/False}` etc.
      - When the user clicks “Undo”, pop the last action and revert it: e.g., for a move, call the same update function to set the task back to old_start/end and redraw. For a link creation, call the unlink function to remove it. This should also maybe push a corresponding “redo” action (the inverse of what was undone) onto a redo stack.
      - Manage the redo stack similarly for a “Redo” button.
      - Caution: if an action in the middle of the stack is something like moving a task that had dependencies and we auto-adjusted others, we need to record all affected tasks in that action so that undo can revert them all. We might simplify by treating each dependent auto-shift as its own action (so undoing one by one is needed), or group them.
      - Ensure that undo actions also call the server API to keep the database consistent with what’s shown (or design the client to not commit to server until user confirms – but Odoo’s likely immediate commit, with undo issuing a corrective update).
      - Test that undo/redo properly handles edge cases (like deleting a task or switching views might clear the history).

   - Defining the view type in Python (inherit Odoo’s view registry if needed, though Odoo Enterprise might already have a gantt view class we can mimic).
   - Load our JS and CSS assets as part of web client.
